# 제8회 금천과학축제 타자왕 설계

작성일: 2026-08-25
작업 브랜치: `geumcheon-2026`
상태: 사용자 승인 설계

## 1. 목적

기존 2026 일잘러 페스타용 Electron 타자왕을 제8회 금천과학축제용으로 확장한다. 참가자에게는 문구와 AI 조건이 무작위로 주어지되, 공식 순위는 문구 길이에 직접 좌우되지 않는 실제 입력 속도로 계산한다. 행사장 PC 10대의 기록은 별도 동기화 프로그램 없이 HTTPS로 사무실 Synology NAS에 모으고, 통신 장애 중에도 기록을 잃지 않는다.

금천 버전은 최종 작업과 검증이 끝날 때까지 원격 GitHub에 푸시하지 않는다. 기존 일잘러 버전의 `main` 브랜치와 릴리스는 변경하지 않는다.

## 4. 저장소와 행사 프로필

코드를 행사별로 복사하지 않고 하나의 공통 소스에 행사 프로필을 둔다. 금천 프로필은 이벤트명, 실행파일명, 색상, 이미지 경로, AI 속도, 문구목록 버전, 개인정보 안내 버전, NAS 이벤트 ID를 소유한다.

권장 구조는 다음과 같다.

```text
events/
  skillup-2026/
  geumcheon-2026/
    event.config.json
    stage_texts.csv
    assets/

services/
  nas-record-api/

deploy/
  synology/

scripts/
  prepare-geumcheon-deployment.mjs
  provision-device-tokens.mjs
```

빌드 시 `EVENT_PROFILE=geumcheon-2026`을 선택한다. 기존 프로필을 선택하지 않은 빌드 동작은 일잘러 버전과 동일하게 유지한다.

금천 런타임 저장소는 기존 공용 경로와 분리한다.

```text
%LOCALAPPDATA%\ThePMD\TypingKing2026\geumcheon-2026\PC01
```

이 경로에는 설정, 암호화 자격증명, 공식·연습 큐, 마지막 리더보드 스냅샷, 비식별 운영 로그가 저장된다. 장치 ID별 경로를 사용하므로 이전 테스트 PC 설정이 다른 폴더의 실행에 섞이지 않는다.

## 5. 전체 아키텍처

```text
PC01~PC10
  Electron renderer
    -> preload IPC
      -> Electron main
        -> Windows DPAPI 암호화 outbox
        -> HTTPS 443
          -> DSM Reverse Proxy
            -> NAS Record API 컨테이너
              -> 검증·재계산·중복 방지
              -> incoming/ai/<record_id>.json

LEADERBOARD01
  Electron main
    -> HTTPS 마스킹 리더보드 조회
    -> 마지막 정상 스냅샷 유지
```

사무실 PC는 이 흐름에 포함되지 않는다. Synology NAS, 사무실 공유기, 사무실 인터넷만 계속 켜져 있으면 된다.

SMB 139/445, DSM 5000/5001, WebDAV와 컨테이너 내부 포트는 인터넷에 공개하지 않는다. 외부 공개 지점은 정상 공인 인증서를 사용하는 HTTPS 443뿐이다.

## 6. 장치 프로필과 자격증명

### 6.1 장치 프로필

각 PC 폴더에는 다음 비민감 정보를 가진 `device-profile.json`을 둔다.

- 프로필 버전
- 이벤트 ID `geumcheon-science-festival-2026`
- 장치 ID `PC01`부터 `PC10` 또는 `LEADERBOARD01`
- 역할 `player` 또는 `leaderboard`
- API 기본 URL
- 공식·연습 세션 설정
- 요청 제한시간
- 재시도 최초·최대 간격

### 6.2 토큰

- PC01~PC10은 서로 다른 256비트 쓰기 전용 토큰을 가진다.
- 플레이어 토큰에는 기록 접수 권한만 있고 조회·수정·삭제 권한이 없다.
- 리더보드에는 별도의 마스킹 조회 토큰을 둔다.
- 운영자 조치가 필요할 때 사용하는 토큰은 리더보드 토큰과 분리하고, 원본 개인정보 조회 권한은 주지 않는다.
- NAS에는 원문 토큰이 아니라 SHA-256 해시와 장치·행사·역할·만료일·허용 세션만 저장한다.
- 모든 토큰 비교는 일정 시간 비교 방식으로 수행한다.

배포 폴더의 최초 실행용 쓰기 토큰은 복사된 PC에서 Windows DPAPI 기반 Electron `safeStorage`로 가져온 뒤 로컬 평문 부트스트랩 파일을 제거한다. 플레이어 토큰은 쓰기 전용이고 행사 종료 시 폐기한다. USB 마스터는 승인된 운영자가 물리적으로 관리하며 GitHub와 NAS 공유폴더에 두지 않는다.

## 7. 기록 저장과 오프라인 재전송

기록 저장은 outbox 우선 방식으로 바꾼다.

1. 게임 결과와 `record_id`를 생성한다.
2. 원본 기록을 Windows DPAPI로 암호화해 공식 또는 연습 outbox에 원자적으로 저장한다.
3. 로컬 저장이 성공하면 게임 결과 화면은 정상적으로 끝낼 수 있다.
4. 즉시 `POST /api/v1/records`를 시도한다.
5. NAS가 반환한 `record_id`와 원본 SHA-256이 요청과 일치하는지 확인한다.
6. 새 저장 성공 또는 동일 내용의 중복 성공일 때만 outbox 파일을 삭제한다.
7. 네트워크 장애, 잘못된 응답, 서버 오류에서는 outbox를 그대로 유지한다.

백그라운드 작업은 앱이 실행되는 동안 독립적으로 동작한다. 2초부터 시작해 최대 60초까지 지수 백오프와 지터를 적용한다. PC마다 큐를 순차 전송해 인터넷 복구 순간 10대가 동시에 NAS를 공격하지 않게 한다.

응답별 처리는 다음과 같다.

- 네트워크 오류와 5xx: 계속 재시도
- 429: `Retry-After`를 존중해 재시도
- 401·403: 자동 반복을 중지하고 운영자 설정 오류 표시
- 409: 충돌 큐로 격리하고 기존 NAS 기록을 보존
- 413·422: 복구 큐로 격리하고 원본을 삭제하지 않음

Windows `safeStorage`를 사용할 수 없으면 개인정보를 평문 큐로 낮추지 않고 공식 게임 시작을 차단한다.

## 8. NAS API

### 8.1 기록 접수

`POST /api/v1/records`

필수 헤더:

- `Authorization: Bearer <device token>`
- `X-Device-Id: PC01`
- `Idempotency-Key: <record_id>`
- `Content-Type: application/json`

요청은 스키마 버전, 이벤트 ID, 공식·연습 세션, 기록을 포함한다. 클라이언트가 NAS 실제 경로를 보내거나 선택할 수 없으며, 서버가 인증된 토큰의 범위와 세션을 이용해 경로를 계산한다.

`record_id`는 플레이어 앱이 `gsc26-<소문자 장치 ID>-<UUID v4>` 형식으로 만든다. 서버는 전체 길이를 80자 이하로 제한하고 정확한 정규식과 UUID 형식을 검증한다. `/`, `\`, `..`, 콜론, 퍼센트 인코딩, 제어문자, Windows 예약 이름과 정규식 밖의 문자는 모두 거부한다. `Idempotency-Key`와 본문의 `record_id`는 완전히 같아야 한다. 서버는 최종 파일 경로를 해석한 뒤 그 부모가 계산된 세션 디렉터리와 정확히 같은지 다시 확인하고, 조건을 통과하지 못한 경로에는 쓰지 않는다.

본문은 32KiB로 제한하고 알려지지 않은 필드를 거부한다. 전화번호, 날짜, 시간, 단계 수, 모드, 문구 ID, AI 속도 범위, 완료 상태의 상호 일관성을 검증한다. 서버는 문구목록을 기준으로 글자 수, 한글 입력 단위, 총시간, 유효 타수, 마스킹 값을 다시 계산한다.

속도 제한은 토큰별 지속 60건/분, 순간 최대 120건으로 적용한다. 행사장 PC들이 같은 공인 IP를 사용할 수 있으므로 IP만으로 참가 기록을 차단하지 않고, IP 제한은 명백한 비인증 공격을 줄이는 보조 수단으로만 사용한다. 브라우저용 CORS는 허용하지 않으며 Electron main 프로세스만 API를 호출한다. 외부 TLS는 1.2 이상만 허용하고 인증서 오류를 무시하는 옵션은 제공하지 않는다.

응답:

- 201: 새 기록 저장
- 200: 동일 ID와 동일 내용의 기존 기록
- 409: 동일 ID지만 다른 내용
- 401·403·413·422·429·503: 인증·크기·검증·제한·저장장치 오류

성공 응답은 기록 ID, 서버 저장 SHA-256, 서버 수신 시각을 포함한다.

### 8.2 리더보드

`GET /api/v1/leaderboard`

행사, 공식·연습, 일차·회차만 조회 조건으로 허용한다. 응답은 다음 표시용 필드만 포함한다.

- 순위
- 마스킹한 참가자명 또는 닉네임
- 전화번호 끝 네 자리 또는 마스킹 표기
- 완주 상태
- 유효 타수
- 총시간
- 완료 시각
- 기록 ID

전체 전화번호, 생년월일, 동의정보, 문구 원문, 관리자 메모는 반환하지 않는다. `ETag`와 `If-None-Match`를 사용하며 변경이 없으면 304를 반환한다. `Cache-Control: no-store`를 사용한다.

통신이 끊기면 리더보드는 마지막 정상 스냅샷과 마지막 갱신 시각을 표시하고 재연결 후 자동으로 따라잡는다.

### 8.3 상태 확인

`GET /health`

외부 응답에는 상태만 노출한다. 컨테이너 내부 readiness는 설정 적재, 토큰 목록 적재, 데이터 폴더 쓰기 가능 여부까지 확인한다. NAS 경로, 버전, 용량과 내부 오류 상세는 외부 응답에 노출하지 않는다.

### 8.4 운영자 조치

인터넷 공개 API는 원본 개인정보 목록, 원본 CSV 다운로드, 개인정보 수정 기능을 제공하지 않는다. 현장 리더보드 운영자는 기록 ID를 기준으로 숨김·숨김 해제만 요청할 수 있고, Electron main의 짧은 관리자 세션과 별도 운영자 토큰을 모두 통과해야 한다. 원본 JSON은 덮어쓰거나 삭제하지 않고 append-only 조치 파일로 상태를 적용한다.

전체 개인정보 CSV가 실제로 필요할 경우 NAS 내부에서만 실행되는 내보내기 명령을 사용하고, CSV 수식 주입 방어를 적용한다. 이 파일은 USB·GitHub·공개 API로 자동 복사하지 않는다.

## 9. 서버 저장 규칙

공식 기록은 다음 경로 규칙을 유지한다.

```text
<data-root>/기록저장/<일차>일차/<회차>회차/incoming/ai/<record_id>.json
```

연습 기록은 다음처럼 분리한다.

```text
<data-root>/기록저장/연습회차/incoming/ai/<record_id>.json
```

저장 절차:

1. 인증과 엄격한 스키마 검증
2. 서버 파생값 재계산
3. 동일 파일시스템에 권한 0600 임시 파일 생성
4. 파일 동기화
5. 덮어쓰기 없는 원자적 게시
6. 기존 ID일 경우 내용 해시 비교
7. 디렉터리 동기화
8. 성공 응답

동일 요청을 반복해도 파일은 하나만 남는다. 같은 ID에 다른 내용이 오면 409를 반환하고 기존 파일을 변경하지 않는다.

서버 로그에는 요청 본문, 이름, 전화번호, 생년월일, 동의정보, Authorization 헤더를 남기지 않는다. 기록 ID, 인증된 장치 ID, 응답 코드, 크기, 처리시간만 기록한다.

## 10. 문구 무작위 배정

초기 문구목록 버전 `geumcheon-draft-20260825-v1`은 실행계획서에서 확인된 주제로 60개를 작성한다. 스테이지마다 20개이며 한글, 숫자, 허용 문장기호만 사용한다. 미성년자에게 유해한 표현을 포함하지 않는다. 사용자가 최종 문구를 제공하면 ID 체계는 유지하고 문구목록 버전을 올려 교체한다.

각 문구에는 변경되지 않는 ID와 문구목록 버전을 부여한다. 각 PC는 스테이지별 shuffle bag을 유지한다. 한 bag의 20개를 모두 소진하기 전에는 같은 PC에서 같은 문구를 다시 선택하지 않는다. bag을 다시 만들 때도 직전 문구가 바로 반복되지 않게 한다.

공식·연습 기록에는 문구 ID, 문구목록 버전과 실제 표시 문구를 함께 남긴다. 서버는 등록된 문구 ID와 원문이 일치하는지 확인한다.

문구 길이를 똑같이 맞추지 않는다. 대신 스테이지가 올라갈수록 문장 구조와 입력량이 대체로 증가하도록 넓은 난이도 구간으로 편성한다.

## 11. AI 난이도

공식 AI 속도 범위:

- Stage 1: 150~200타/분
- Stage 2: 200~250타/분
- Stage 3: 250~300타/분

연습 AI 속도 범위:

- Stage 1: 100~150타/분
- Stage 2: 150~200타/분
- Stage 3: 200~250타/분

각 스테이지에서 범위 안의 AI 속도를 무작위로 선택하고 실제 선택값을 기록한다. AI 속도는 대결의 재미와 성공 여부에 영향을 주지만, 완주자끼리의 공식 순위에는 직접 사용하지 않는다.

## 12. 공식 순위

문구마다 입력량이 다르므로 총시간을 1차 기준으로 사용하지 않는다. 별도의 임의 가중 점수도 만들지 않는다.

완주자의 유효 타수는 다음과 같다.

```text
유효 타수 = 전체 한글 입력 단위 × 60,000 / 전체 실제 입력시간(ms)
```

한글 입력 단위는 프로그램이 실제 타수 표시에 사용하는 자모·숫자·문장기호 입력 단위다. 따라서 짧은 문구를 받은 참가자의 총시간이 짧다는 이유만으로 높은 순위를 얻지 않는다.

공식 스테이지 시간은 카운트다운이 끝나고 입력창이 활성화되는 순간의 단조 증가 시계 `performance.now()`에서 시작한다. 정확한 문장 완성, AI의 스테이지 승리, 중단 확정 중 먼저 발생한 시점에 끝난다. 카운트다운과 스테이지 사이 결과 애니메이션은 제외한다. 한글 IME 조합, 오타 수정, 백스페이스, 입력 정지, 창 포커스 이탈과 중단 확인창에 머문 시간은 공식 시간에 포함하며 공식 모드에는 타이머 일시정지 기능을 두지 않는다. 성공 기록의 전체 실제 입력시간은 세 스테이지 `user_time_ms`의 합이다. 실패 기록은 종료된 스테이지와 마지막 스테이지의 실제 경과시간을 각각 보존한다. 디버그 모드 기록은 항상 테스트 기록으로 표시하고 공식 순위에서 제외한다.

공식 정렬 순서:

1. AI 3개 스테이지 완주자
2. 소수점 이하를 버리지 않은 유효 타수 내림차순
3. 전체 입력 단위 내림차순
4. 총시간 오름차순
5. 완료 시각 오름차순
6. 기록 ID 오름차순

예를 들어 10초·600타/분 기록보다 11초·700타/분 기록이 높은 순위다.

완주하지 못한 기록은 모든 완주자 아래에서 도달 스테이지, 진행률, 유효 타수 순으로 정렬한다. 중단 기록은 일반 실패 기록 아래에 둔다.

공식 도전은 참가자 식별키별 행사 전체 최초 3회까지만 순위 대상이다. 성공, 실패, 중단을 모두 1회로 계산하며 서버 수신시각과 기록 ID로 순서를 확정한다. 네 번째 이후 공식 기록도 원본에는 보존하지만 `순위 대상 아님`으로 표시한다. 참가자는 연습모드에서 횟수 제한 없이 플레이할 수 있다. 공개 공식 리더보드는 최초 3회 안의 최고 기록 한 건만 표시한다. 참가자 식별키는 서버 비밀키로 정규화 전화번호를 HMAC 처리해 만들며 원본 전화번호를 노출하지 않는다. 모든 참가자를 화면에 표시하고 화면 높이를 넘는 경우 스크롤한다. 전체 도전 기록과 공식 시도 순번은 원본 저장소에 보존한다.

### 12.1 순위 형평성 검증 게이트

순위 구현보다 먼저 독립 시뮬레이션 테스트를 작성한다. 생산 리더보드 활성화 조건은 다음과 같다.

- 동일한 잠재 입력 속도에서 60개 모든 문구와 모든 shuffle seed의 계산 유효 타수 편차가 반올림 오차 1타/분 이내다.
- 오타가 없고 타이머 잡음이 없는 조건에서 잠재 속도가 5% 이상 빠른 참가자가 느린 참가자보다 아래로 내려가는 경우가 0건이다.
- 10초·600타/분과 11초·700타/분을 포함한 경계 사례에서 700타/분 기록이 항상 우선한다.
- 최초 3회만 순위 대상이고 네 번째 이후 기록이 최고 기록 선택에 들어가지 않는다.
- 문구 순서와 장치별 shuffle seed를 바꿔도 동일 입력 데이터의 순위가 바뀌지 않는다.
- 스테이지별 문구 난이도 편차는 최소 5명의 내부 파일럿이 각 스테이지의 대표 문구를 교차 입력해 확인한다. 문구별 중앙 유효 타수가 해당 스테이지 중앙값에서 15%를 초과해 벗어나면 그 문구를 수정하거나 제외한 뒤 다시 측정한다.

이 게이트가 실패하면 임의로 산식을 바꾸지 않고 실패 데이터와 대안을 사용자에게 보고해 재승인을 받는다.

## 13. 개인정보와 관리자 보안

공식 게임은 사용자가 요청한 이름 또는 닉네임, 휴대폰번호, 생년월일, 동의정보를 수집하도록 구성한다. 연습모드의 수집 항목도 행사 운영 승인값으로 설정할 수 있으나 공식·연습 데이터는 분리 저장한다.

개인정보 안내의 기본 역할 표기는 다음 원칙을 따른다.

- 개인정보처리자: 서울특별시 금천구
- 처리업무 수탁자: 주식회사 더피엠디

실제 화면 문구, 만 14세 미만 법정대리인 동의 처리, 보유기간, 파기일은 금천구의 서면 승인값으로 행사 프로필에 넣는다. 생산 배포 생성기는 승인된 안내 버전과 보유 만료일이 없으면 최종 배포본을 만들지 않는다. 개발용 테스트에는 실제 참가자 개인정보를 사용하지 않는다.

`0208`은 행사장 로컬 운영 화면의 PIN으로만 사용한다. 원격 NAS 토큰이나 DSM 비밀번호로 재사용하지 않는다. Electron main은 PIN 성공 후 짧은 관리자 세션을 만들고, 숨김·내보내기·설정 변경 등 모든 privileged IPC에서 세션을 다시 확인한다. renderer에는 NAS 토큰을 전달하지 않는다.

공개 리더보드 renderer에는 원본 전화번호와 생년월일을 전달하지 않는다. NAS와 백업 공유폴더는 API 서비스 계정, 승인 운영 담당자, 백업 계정만 접근하도록 ACL을 제한한다. NAS 공유폴더와 백업은 암호화하고 보유기간 만료 시 원본, 스냅샷, 백업을 함께 파기한다.

## 14. Synology 배포

NAS 서버는 Synology Container Manager에서 단일 비루트 컨테이너로 실행한다.

- Node.js 24 LTS 기반 amd64·arm64 이미지
- 재시작 정책 `unless-stopped`
- root filesystem 읽기 전용
- `/tmp`만 tmpfs
- Linux capability 전체 제거
- `no-new-privileges`
- 데이터 폴더만 쓰기 마운트
- 행사·토큰 설정은 읽기 전용 마운트
- 컨테이너 포트는 NAS 내부에서만 접근
- DSM Reverse Proxy가 외부 HTTPS 443을 전달

실제 NAS 설치 완료 판정에는 NAS 모델·DSM 버전·Container Manager 지원, CPU 아키텍처, 실제 볼륨 경로, 공인 IP 또는 CGNAT 여부, 도메인·DDNS, 인증서, 443 사용 현황, 방화벽·ACL 확인이 필요하다. 이 값들은 일반 코드 구현을 막지 않지만 실제 NAS 작동 완료 주장에는 반드시 현재 장비 증거가 필요하다.

각 플레이어 폴더에는 동일한 전체 Electron 런타임, AI 게임, AI 연습모드, 금천 행사 자료, PC별 프로필과 해당 PC 쓰기 토큰만 넣는다. LEADERBOARD01에는 두 리더보드와 읽기·운영자 프로필만 넣는다.

현재 런타임 기준 예상 총용량은 약 6.4GiB이므로 16GB 이상 USB를 사용한다. 설치일에는 USB에서 직접 실행하지 않고 각 폴더를 해당 렌탈 PC의 바탕화면으로 복사한다. 브라우저에서 행사장 Wi-Fi 캡티브 포털 승인을 마친 뒤 앱의 서버 연결 확인을 실행한다.

NAS 서버 설정, 토큰 해시 매니페스트, 전체 원문 토큰 목록은 USB 마스터와 분리한 비공개 운영 묶음으로 관리한다.

## 16. 오류 표시와 운영 UX

- 플레이어: 로컬 저장 완료와 NAS 반영 완료를 구분한다.
- 네트워크 장애: `기록은 이 PC에 안전하게 보관되었으며 연결 복구 후 자동 전송됩니다.`라고 표시한다.
- 인증 오류: 자동 재시도를 멈추고 PC ID와 설정 점검을 요구한다.
- 리더보드 장애: 마지막 정상 순위를 유지하고 연결 끊김 및 마지막 갱신 시각을 표시한다.
- 운영 화면: PC ID, 서버 상태, 미전송 건수, 마지막 성공 전송 시각, 공식·연습 구분을 표시한다.
- 렌탈 PC 반납 전: 모든 PC의 미전송 건수가 0인지 확인하고 로컬 데이터·DPAPI 토큰 정리 절차를 실행한다.

정리 기능은 앱이 종료된 상태에서 승인된 운영자만 실행한다. 대상은 현재 장치의 금천 전용 `userData`·런타임 루트, DPAPI 자격증명, 공식·연습 outbox, 복구·충돌 큐, 리더보드 스냅샷, 비식별 로그와 바탕화면에 복사한 실행 폴더다. Electron `userData`도 금천 장치별 런타임 루트 아래로 명시적으로 지정해 다른 앱 데이터나 기존 일잘러 데이터를 건드리지 않는다.

정리 도구는 먼저 공식·연습·복구·충돌 큐가 모두 0건인지 확인한다. 한 건이라도 남았거나 파일 삭제가 실패하면 실패 영수증을 만들고 정리를 중단하며 해당 렌탈 PC를 반납 가능 상태로 표시하지 않는다. 운영자는 NAS 복구, 휴대폰 핫스팟 또는 승인 네트워크로 전송을 완료한 뒤 다시 실행한다. 성공 시 PC ID, 삭제 대상별 건수, 완료시각과 결과만 포함한 비개인정보 정리 영수증을 USB 운영 폴더에 저장하고 대상 경로가 존재하지 않는지 재검사한다. 일반 파일 삭제만 수행하므로 저장장치 수준의 보안 삭제를 완료했다고 표현하지 않는다.

## 17. 테스트와 완료 기준

### 17.1 자동 검증

- 문구 shuffle bag이 한 주기 안에서 중복되지 않음
- 무작위 문구·길이·shuffle seed·최초 3회 정책에 대한 12.1절 형평성 시뮬레이션 통과
- 공식·연습 큐와 세션이 섞이지 않음
- 유효 타수와 모든 순위 타이브레이커
- 10대 동시 고유 기록이 각각 한 파일로 저장됨
- 동일 기록 100회 순차·동시 재전송 시 파일 하나
- 동일 ID·다른 내용은 409이고 원본 무변경
- 토큰 없음·오류·폐기·장치 사칭 거부
- 쓰기 토큰으로 조회 불가, 읽기 토큰으로 쓰기 불가
- 잘못된 날짜·시간·전화번호·문구 ID·AI 범위·추가 필드·과대 본문 거부
- 인터넷 중단, 앱 재시작, NAS API 재시작 후 큐 전부 복구
- 성공 응답의 ID와 해시 확인 전 큐 삭제 없음
- 401·403 정지, 429 Retry-After, 5xx 백오프
- 로그·리더보드 응답·renderer에서 원본 PII와 토큰 검색 결과 0건
- CSV 수식 주입 방어
- 기존 일잘러 논리·빌드 회귀 없음

### 17.2 화면·패키지 검증

- 1366×768, 1920×1080
- Windows 배율 100%, 125%, 150%
- AI 게임, 공식 리더보드, 연습 AI, 연습 리더보드 전 화면
- 키비주얼 이미지 선명도, 글자 겹침, 스크롤, 포커스, 한글 IME
- PC01, PC10, LEADERBOARD01 격리 실행
- 네 개 실행파일명·아이콘·창 제목·제품 설명
- 배포본 데이터 폴더가 비어 있고 실제 기록·로그·개인정보가 없음
- SHA-256 매니페스트와 실제 파일 일치

### 17.3 실제 현장·NAS 검증

- NAS 재부팅 후 API 자동 시작
- 사무실 PC를 끈 상태에서 휴대폰 데이터망으로 공식·연습 저장 및 조회
- 실제 행사장 Wi-Fi에서 HTTPS 443, DNS, 캡티브 포털 확인
- 외부에서 139·445·5000·5001과 컨테이너 포트가 닫혀 있음
- 10대 동시 기록과 리더보드 반영
- 인터넷 차단 후 기록 누적, 복구 후 자동 따라잡기
- 렌탈 PC 반납 전 미전송 0건과 로컬 삭제
- 정리 성공·실패 영수증과 금천 전용 로컬 경로 부재 확인

실제 NAS·행사장 검증이 수행되지 않은 상태에서는 코드와 로컬 통합 테스트가 통과해도 `NAS 배포 완료` 또는 `현장 운영 준비 완료`라고 보고하지 않는다.

## 18. Git·비밀정보 규칙

추적 가능:

- 공통 소스
- 금천 행사 프로필의 비밀이 아닌 항목
- 디자인 자산과 임시 문구
- 서버 소스·Docker·Compose 예시
- 토큰 생성기와 배포 생성기
- 비밀값이 없는 설정 예시
- 자동 테스트와 운영 문서

추적 금지:

- 실제 NAS 도메인·내부 볼륨 경로가 담긴 운영 설정
- 원문 토큰, 토큰 해시 운영 매니페스트, `.env`
- 실제 장치 자격증명과 최종 USB 배포본
- 참가자 기록, 로컬 큐, 복구·처리 영수증
- 원본 개인정보 CSV, 로그, 백업, 스냅샷

금천 브랜치는 최종 작업 완료 후 사용자가 업로드를 다시 승인할 때까지 로컬에만 둔다.
